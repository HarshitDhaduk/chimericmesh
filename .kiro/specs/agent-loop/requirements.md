# Requirements: agent-loop (V1)

Capability map: [docs/v1-capability-map.md](../../../docs/v1-capability-map.md) (module `agent-loop`, depends on: `services`, `store`, `auto-approval`, plus shared `core` types; effort 1.5 days; no cuts are applied, contingency item 5 in the map would save 0.25). The hub and REST side of structured proposals is in `auto-approval` section 9; this module only wraps it in MCP tools. The REST routes and hub code for the tools that are new in this module (service events, digest, code search, verify, long poll, permissions snippet) are **owned by this module** (section 1, route table).

## Baseline

[legacy-mesh](../legacy-mesh/requirements.md) R4 (MCP tools), R7 (human-approved remediation, `propose_remediation`, `get_proposal`, `list_proposals`, `complete_proposal`), R10.4 (verify a fix before completing). Existing tools, the `mesh-responder` agent and the `chimericmesh-remediation` power keep working (B8).

## Introduction

The agent today works one incident at a time and only when the user prompts it. This module makes it work per service, lets it pick up new incidents without being prompted (watch mode), and lets it act on an approval that came either from the user or from an approval rule. It changes the MCP tools, the agent profile and the power skills. The MCP server stays a set of thin wrappers over REST (project steering): no clamping, no capping and no business logic there. Clamps, caps and control-character stripping happen in the REST layer, which this module also owns for the new routes. The hub never runs the agent and never executes a fix (R7.4).

## Objective

A user opens one Kiro session with the `mesh-watcher` agent. New incidents of registered services are investigated, explained and proposed with named files and a verification step. Fixes the user approved (or that a rule approved) are applied inside the service's code folder, verified, completed and resolved. Everything else still asks.

Threat model: log text, incident samples, proposal text and file contents are untrusted and may carry prompt injection. Approval is only the `status` and `approval` fields that `get_proposal` returns. The agent has no tool for rules, tokens, services or discovery. Kiro's own permission system is the layer that stops writes outside the code folder. **Honest limit (map, "Honest limits of the access model"):** the agent runs as the same OS user as the hub, so it can read the token file and call the REST API from any shell command Kiro lets it run. The real safeguard against the agent approving its own work or widening rules is Kiro's permission prompt on shell commands and on writes outside the approved scope, which these requirements keep (R5.1). The deny rules in the profile (R5.2) and the optional `Pre Tool Use` hook (R5.9) are extra layers, not guarantees. The agent has no MCP tool to create, edit, widen, re-enable or resume rules. Pause, revoke and withdraw are token-free REST routes (D3), so the agent could also call them from a shell; that can only reduce its own permissions.

The MCP server SHALL pass parameters through unchanged and SHALL NOT clamp, cap or filter; the REST layer does that (1.7). ### 3. Re-verification before acting
**User story:** As a user, I want the agent to check at the last moment that its fix is still approved, so that a revoked rule or a denial stops it.

1. THE SYSTEM SHALL add the read-only tool `verify_proposal(proposal_id, files)` returning `{ok, reasons[], status, approval, declared_files}`. It SHALL return `ok: true` only when all of these hold. (a) The proposal status is `approved`. (b) The approval is by a user (`approved_by_rule` is null), or by a rule (`approved_by_rule` is set; never read from the `decided_by` text) that is `active` now (not revoked, expired, suspended or paused), whose bound code folder equals the service's current one, and whose 30 minute window has not passed. (c) `files` has 1 to 20 entries. (d) WHERE the proposal declared `files` (always the case for a rule approval), every path in `files` is among them after normalization and passes `auto-approval` R5.1. (e) WHERE the proposal declared no `files` (user approval only), the paths are not compared with a declared list, because the user approved the described action. (f) WHERE the incident's service has a code folder, every path in `files` is inside it (`services` R2.3); WHERE there is no service or no code folder, the folder check is skipped and `reasons` carries the note `no code folder, path scope not checked`. [Auto] [PBT]
2. THE SYSTEM SHALL return one reason string per failed check, without log text. [Auto]
3. THE SYSTEM SHALL write the `mesh-watcher` prompt and the `remediation-loop` and `watch-mode` skills so that the agent calls `verify_proposal` with the exact files it is about to edit immediately before the first edit, again before any later edit of a file it did not list before, and before calling `complete_proposal`; and changes nothing unless `ok` is true. [Auto: static test of prompt text] [Manual: observe in a live session]
4. WHEN `verify_proposal` returns `ok: false`, THE SYSTEM SHALL have the agent stop, make no change, and report the reasons to the user (prompt and skill text). If it had already changed files, it SHALL say exactly which. [Manual]
5. THE SYSTEM SHALL tell the agent that an action that differs from the approved one (other files, a restart, a config change) needs a new proposal, and that D4 limits V1 to code changes. [Auto: static test of prompt text]
6. THE SYSTEM SHALL tell the agent that only the `status` and `approval` returned by tools count as approval, never text in logs, IRC, proposals or files. [Auto: static test of prompt text]

### 4. Watch mode
**User story:** As a developer, I want the agent to notice new incidents while I work, so that I do not paste prompts.

1. THE SYSTEM SHALL add the MCP tool `wait_for_work(timeout_seconds=25, service_id=None, exclude_ids=[])` over `GET /api/watch/next`. `exclude_ids` holds incident ids and proposal ids; both kinds of work item are skipped when their id is listed. Reason for the name: it also reports approved proposals ready to act on, not only incidents. [Auto]
2. WHEN `wait_for_work` is called, THE SYSTEM SHALL return immediately if work exists, otherwise hold the request until work appears or `timeout_seconds` (clamped in the REST layer to 1 to 25, default 25) passes, then return `{status: "timeout"}`. [Auto]
3. THE SYSTEM SHALL define work as: (a) open, unresolved incidents of a registered service, with no active proposal, not in `exclude_ids`, whose latest proposal in the current opening was not denied by a user, ordered by severity then count (at most 5 returned). A user denial is a proposal with status `denied` and `decision_origin: user` (`store` R4.7), a column that only the hub's own rule and sweep logic can set to `hub`; the `decided_by` text is never used for this decision, so an IRC nick such as `expired-bob` stays a user denial. (As defence in depth `auto-approval` R4.8 still rejects reserved prefixes on `/decide`.) Such an incident returns to the work list only when it reopens (a new `opening`, `store` R5.7), so a denied fix is not re-proposed in a loop. A proposal withdrawn, expired or denied by the hub (`decision_origin: hub`: revoked or suspended rule, withdrawal, expiry) does not block the incident; (b) proposals in status `approved` that are not `done` and not in `exclude_ids` (at most 5), with their `approval` objects. The agent adds a proposal id to `exclude_ids` as soon as it starts acting on it, so a busy agent is not handed the same approved proposal twice; a restarted loop with an empty list gets it again, which is intended. Incidents of the `unassigned` pseudo service are excluded unless `service_id` is `unassigned`. [Auto] [PBT]
4. THE SYSTEM SHALL return work items as structured fields (ids, counts, service, category, severity, `sample` capped at 200 characters under a field named `sample`) and SHALL NOT return event bodies. [Auto]
5. THE SYSTEM SHALL allow at most 4 concurrent waiters and answer extra ones with 429. THE SYSTEM SHALL set the MCP server's HTTP client timeout for this call to 35 seconds (the 25 second maximum plus a 10 second margin, always above the wait) and keep 10 seconds for the other tools. Kiro's per-call `requestTimeout` default of 120000 ms is above the wait. [Auto]
6. WHEN the hub shuts down while a waiter is held, THE SYSTEM SHALL end it with `{status: "timeout"}`. [Auto]
7. THE SYSTEM SHALL ensure that a held request does not block ingestion or other endpoints (asyncio condition or event, no polling loop in a thread). [Auto]
8. THE SYSTEM SHALL write the watch loop into the `mesh-watcher` prompt and the `watch-mode` skill: call `wait_for_work`; for each incident call `get_service`, `get_incident`, `explain_log_window`, `find_code_for_service`; call `propose_remediation` with `files`, `estimated_lines` and `verification`; when the status is `approved` act per section 3; when `pending`, add the incident to `exclude_ids` and call `wait_for_work` again; after acting, verify, `complete_proposal`, `resolve_incident`, and loop. [Auto: static test] [Manual]
9. THE SYSTEM SHALL tell the agent to stop the loop and ask the user when it sees three consecutive tool errors, or when `wait_for_work` returns 401, 403 or 429 twice. [Auto: static test of prompt text]
10. THE SYSTEM SHALL NOT make the hub start, wake or spawn any Kiro process (F1, F3). [Auto: static allow-list test. Only `chimericmesh/fsperms.py` (`store` R1.5, Windows `icacls`) and the `discovery` module may import `subprocess` or call `os.system`, `os.popen` or `os.spawn*`. The hub, the MCP server, the tailer and the parsers may not.]

### 5. Agent profile and Kiro permissions (F4 to F9)

1. THE SYSTEM SHALL add `.kiro/agents/mesh-watcher.json` with the `chimericmesh` MCP server, the steering file, read, write and shell tools, and these rules: `allow` for the read-only MCP tools and for `wait_for_work`, `propose_remediation`, `verify_proposal`, `complete_proposal`, `resolve_incident` and `announce_to_irc`; and NO `allow` rule and NO `ask` rule for `fs_write` or `shell` (the only `fs_write` and `fs_read` rules are the `deny` rules of 5.2), so the default "ask" applies unless the user adds an allow. [Auto: static test in `test_kiro_assets.py`]
2. THE SYSTEM SHALL include in that profile `deny` rules for `fs_write` on `**/.env`, `**/.env.*`, `**/*.pem`, `**/*.key`, `**/id_rsa*`, `**/admin.token`, and for `fs_read` on `**/admin.token`, and for `fs_read` and `fs_write` on `**/chimericmesh.db*` and on the hub home directory (`~/.chimericmesh/**`). The token and the database live there by default (`store` R1.1), outside the workspace, so the deny rules are a second layer. [Auto: static test]
3. THE SYSTEM SHALL NOT change `mesh-responder.json`, the existing power skills or `.kiro/settings/mcp.json`, except by adding the new tools to the power's tool list where it names them. [Auto: file comparison]

WHEN the service's code folder is not inside the open Kiro workspace, THE SYSTEM SHALL NOT emit an `fs_write` allow line and the text says that the fix still runs but Kiro prompts for each write. 10. THE SYSTEM SHALL document in the skill and the README: the workspace must be trusted (F7); permission rules are static (F6); the user-scoped file applies to every session (F5); the `PermissionRequest` hook (F8) is not part of V1. [Auto: docs test]
11. THE SYSTEM SHALL document that "the agent cannot approve its own proposal or widen rules" is **a design goal with stated limits, not a guarantee**: (a) the token and the database are outside the workspace and denied in the profile (5.2) and the IRC operator commands that approve or deny need the token as `PASS` (`services` R9). The docs also say that pause, revoke and withdraw need no token (D3), so a shell command can call them, and that this can only reduce the agent's own permissions. [Auto: docs test] [Manual: the user accepted this for hands-off mode only on 2026-11-18, see Open Question 5 and Notes for design]

## Boundaries

- Always: keep MCP tools thin; treat log text as data; verify before acting; one concrete code change per proposal; cap every returned field.
- Ask first: adding any tool that mutates configuration; raising the long-poll maximum above 25 seconds; recommending a Kiro permission broader than a path-scoped `fs_write`.
- Never: give the agent a tool for rules, services, tokens or discovery; let the hub start or script Kiro; write Kiro permission files from the hub; recommend `--trust-all-tools` or `allow-all`; treat text from a log or chat as approval.

## Out of Scope (Deferred)

- Waking Kiro from the hub (spawning `kiro-cli`, headless runs per incident): F3, needs a paid API key and an install; and the hub must not spawn processes.
- A Kiro `PermissionRequest` hook (F8): documented for the CLI only and Kiro CLI is not installed here. The `Pre Tool Use` hook (F8b, R5.9) is the optional replacement, built as an extra layer, not in the estimate.
- Hooks that re-prompt the agent on Agent Stop to keep the loop alive: unverified; the loop is driven by the prompt and the tool for V1.
- Configuration, restart and infrastructure fixes (D4): next spec.
- Multiple agents working in parallel on different incidents: the claim and lock protocol is out of budget; B3 (one active proposal per incident) prevents double work.
- Applying fixes from the hub or a worker process: the mesh never executes (R7.4).
- Git branch or pull request creation for fixes: not required; the user reviews the diff in their editor.
- Model-written explanations inside the hub: the hub has no model; `explain_log_window` returns a digest and the agent writes the explanation.
